## Ground 1 (decisive): the Graphify MCP was never invoked, not once

Scanned every Claude Code session log under `~/.claude/projects/` (2,967 `.jsonl`
files) for the whole post-install window (2026-07-02 install → 2026-07-16):

| Measurement | Count |
|---|---|
| jsonl files scanned | 2,967 |
| session logs listing the 10 `mcp__graphify-volpred-codeonly__*` tools | ~803 |
| **actual `tool_use` blocks invoking any graphify tool** | **0** |
| sessions that invoked graphify at least once | 0 |

Method: parsed each JSONL record and counted only `message.content[]` blocks with
`type == "tool_use"` and a `name` containing `graphify`. This deliberately
separates *real invocations* from *incidental string matches*. The incidental
matches are all explainable and none are usage:

- `ls`/`Bash` tool_result output that happens to list the `graphify-out/` directory
- dispatch starvation banners naming this very task id
- this verdict task's own prompt text
- deferred-tool-list `attachment` records enumerating available tool names

Interpretation: registration was live and correct (verified present in
`~/.claude.json` under project scope), the graph artifact existed (4.9 MB
`graph.json`, 4,837 nodes / 12,129 edges), the binaries were installed — and no
agent ever called it. **Token reduction attributable to Graphify is therefore 0%
by construction, not by estimation.** 0% < 10% → remove.

Net token effect was mildly *negative*: the 10 graphify tool names were carried in
the available-tool list of ~803 sessions with zero offsetting use. This report does
not quantify that overhead in tokens — no measurement isolates it, and no number is
invented here. Direction is negative; magnitude is small and unmeasured.

The pilot's headline "29.3x reduction" from `run_manifest.json` is a **vendor
self-benchmark on a synthetic corpus** (`graphify token reduction benchmark`), not
an observation of this repo's agents. It never had a chance to transfer, because
nothing ever queried the graph.

## Ground 2 (independent): the baseline was not usable for a 10% test anyway

`token_baseline.json` declares:

- `metric_scope`: "platform_ops category from scripts/token_usage_report.py"
- `honesty_note`: "Current token_usage reports do not isolate hourly-dispatch
  sessions; platform_ops is the closest reproducible proxy for this pilot."

The task's comparison ("post-install platform_ops/hourly-dispatch token proxy vs
baseline, threshold 10%") cannot be executed against this file. Four defects:

**2a. No designated baseline value and no comparison rule.** The file lists three
candidate rows, never says which one is *the* baseline, never specifies which
metric is authoritative (`billable_total` vs `billable_total_per_message` vs
`estimated_cost_usd_per_message`), and never defines an aggregation or the
arithmetic for the 10% test.

**2b. The candidates disagree by 3.3x, so the verdict would be an artifact of the choice.**

| Baseline row (as recorded) | msgs | billable_total | per-message |
|---|---|---|---|
| weekly_2026-06-26 | 128 | 1,289,625 | 10,075.20 |
| weekly_2026-06-28 | 145 | 1,230,291 | 8,484.77 |
| daily_2026-06-30 | 61 | 216,545 | 3,549.92 |

Post-install, same metric, same generator:

| Post window | msgs | billable_total | per-message |
|---|---|---|---|
| weekly_2026-07-05 (07-05 → 07-12) | 101 | 303,923 | 3,009.14 |
| weekly_2026-07-12 (07-12 → 07-19) | 74 | 133,909 | 1,809.58 |

Picking weekly_2026-06-26 as baseline yields "~70-82% reduction". Picking the
*current* content of weekly_2026-06-28 (3,080.78/msg, see 2d) yields "~2%". Same
data, same window, opposite verdicts across the 10% line. A test whose outcome is
set by an undocumented choice is not a test. **None of these numbers are quoted
here as the pilot's effect, because Ground 1 shows the cause was absent.**

**2c. Two of three baseline windows contain post-install days.** Install was
2026-07-02. `weekly_2026-06-26` covers 06-26 → 07-03 and `weekly_2026-06-28`
covers 06-28 → 07-05 — both straddle the install date. The "before" contains the
"after". Only `daily_2026-06-30`'s label is pre-install, and its own `window`
field reads 06-28 → 07-05, straddling too.

**2d. The baseline snapshot no longer reproduces from its own source file.**
Re-reading `storage/reports/token_usage/weekly_2026-06-28.json` today gives
58 messages / 178,685 billable / 3,080.78 per-message — versus the
145 / 1,230,291 / 8,484.77 recorded in `token_baseline.json`. The report was
regenerated on Jul 6 (mtime), four days after the Jul 2 capture, overwriting the
window the baseline had pinned. (`weekly_2026-06-26` and `daily_2026-06-30` do
still reproduce exactly.) A baseline whose source mutates underneath it cannot
anchor a follow-up test.

Per the task's own rule — "if the baseline file does not define the metric clearly
→ record the design flaw as *pilot design defect: no comparable baseline*, which is
itself a valid verdict → treat as failing the 10% bar" — Ground 2 alone mandates removal.

## Lesson for future pilots (not written to knowledge.json — K1259)

The failure here was not Graphify's efficacy — that remains untested. It is that a
tool was installed and then measured with (a) a proxy metric the baseline file itself
flagged as non-isolating, (b) baseline windows overlapping the treatment, and
(c) **no adoption check**. A pilot that can register a capability but never verify a
single call spent 14 days measuring noise. Any future tool pilot should gate on a
usage counter first: if invocations == 0, the efficacy question is moot and the
verdict is immediate.
