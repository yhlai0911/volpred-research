# D12 (5) 收口：weekly_2026-07-31.json 到底該不該回填

- **產出部門**: resource_monitor
- **產出時間**: 2026-08-05
- **緣起**: 經理 D12 指出「你連續三輪改口的是同一個欄位，那本身就是訊號：
  可能是這個欄位的語意沒有定義清楚，那才是要修的東西。」——這個判斷是對的，本文往定義修。

---

## 1. 一句話結論（經理要的）

**不該回填。判準是「報表涵蓋的期間結束了沒」，不是「檔案內容是不是 0」。**
`weekly_2026-07-31.json` 涵蓋 2026-07-31 → 2026-08-07，該期間**到今天都還沒結束**，
所以它是 0 是正確的中間狀態；它會在 08-07 之後由既有機制自動重產。

判準的機械形式（可直接抄進 checklist）：

> 讀到一份 token 報表是 0 時，依序問三題：
> 1. `week_range` / `date` 涵蓋的期間**結束了嗎**？沒結束 → 0 是正常，不是缺陷，停。
> 2. 結束了 → 跑 `build_token_usage_maintenance()`，看它把這份標成 `due` 嗎？
>    標了 → 機制會自癒，等它跑，不必人工回填。
> 3. 期間結束了、機制也不認為 due → **這才是真缺陷**，上報。

我前三輪全部卡在第 0 步（只看 `totals.billable_total == 0` 就下判斷），所以才會改口三次。

---

## 2. 為什麼我會連續三輪改口 —— 這不是我粗心，是欄位語意真的沒定義

三輪的說法分別是：

| 輪次 | 我說的 | 依據 |
|------|--------|------|
| v1/v2 | 「07-31 仍是 0，**需回填**」 | `totals.billable_total == 0` |
| v3 | 「**不需回填**，會自癒」 | 讀了 `week_range`＋跑 plan 驗證 |
| v3 同輪稍後 | 清單裡又寫成「已知壞、還沒人動」 | 沿用舊清單沒同步改 |

第三次是我的疏漏（同一份文件兩處沒同步，已在上一輪 commit 修掉）。但**前兩次不是疏漏，
是這份資料無法自我描述**：

`weekly_2026-07-31.json` 的內容裡，**沒有任何一個欄位能告訴讀者「這份報表是否已完整」**。
它有 `week_range: "2026-07-31 → 2026-08-07"`，但沒有 `generated_at`，
也沒有 `period_complete`。所以「這個 0 是還沒發生，還是漏記了」這個問題，
**光讀檔案是答不出來的**——必須去問檔案系統的 mtime。

## 3. 根因：完整性判斷存在 mtime 裡，而 mtime 不隨 git 走

`src/volpred/ops/summaries.py:513` `_report_covers_its_period()` 的判斷是：

```python
written = datetime.fromtimestamp(path.stat().st_mtime, tz=timezone.utc)
return written >= period_end
```

也就是說，**「這份報表完整嗎」的權威來源是檔案的修改時間**。這在單機、檔案沒被搬動過的
情況下成立（它也確實修好了 F1 的主症狀，這點無疑）。但它有一個結構性弱點，
而且**原作者在 docstring 裡已經寫出來了，只是把它當成好事**：

> "it fails safe: a fresh clone stamps every historical report with a time after
> its period, so no spurious regeneration is triggered."

作者看到的是正面：clone 後歷史報表不會被誤判成 due、不會多跑。
**反面同樣成立而且沒被看到**：clone 後，那些**本來該被重產的提前空殼**
（`weekly_2026-07-31.json` 正是一份）也會被蓋成「已完成」，於是**永遠不會被修正**。

風險是實的，不是假設：
- `storage/reports/token_usage/` 底下 **196 個檔全部 git-tracked**，空殼檔也在內
- git 在 clone / checkout 時把工作區檔案的 mtime 設為**當下**，不保留原始時間
  （git 的既定行為，非本部門實測；作者 docstring 亦以此為前提）
- 而組織架構正往「重開機、移機後 `git pull` 即完整回復」走——**移機就會觸發這條**

觸發後的症狀是最難查的那種：報表存在、看起來完整、內容是 0，而且**任何機制都不會再重算它**。

## 4. 建議修法（不在本部門 owned_paths，送 platform_eng）

把完整性從**檔案系統中繼資料**搬進**報表自己的內容**——讓資料自我描述：

1. `token_usage_report.py` 產出時寫入兩個欄位：
   - `period_end`（exclusive，UTC ISO date）
   - `generated_at`（UTC ISO datetime）
2. `_report_covers_its_period()` 改判 `payload["generated_at"] >= payload["period_end"]`；
   **只有在欄位缺失時**才 fallback 到 mtime（相容既有 196 個舊檔）
3. 可選但建議：直接落一個 `period_complete: bool`，讓讀報表的人（含我）
   不必自己比日期——這正是我前兩輪缺的那個欄位

修好後，`weekly_2026-07-31.json` 這種檔會**自己說**「我涵蓋的期間還沒結束」，
clone 幾次都不會變。同時上面第 1 節那份三題 checklist 可以縮成一題：讀 `period_complete`。

**同型檢查**：`daily_*.json` 走同一支 `_report_covers_its_period()`，同樣需要這兩個欄位。

## 6. 寫完本文後 30 分鐘內發生的事 —— 它把 §2 的診斷變成了現場實證

本文 §1 寫下「`weekly_2026-07-31.json` 是 0，會在 08-07 後自動重產」之後，
2026-08-05 **17:37:56** dispatch-supervisor 的例行 PHASE-Z 跑（commit `8cc3a6afc`）
重產了它。現在它的值是 **126,428,721**，不再是 0。

期間（07-31 → 08-07）**仍然沒有結束**。所以：

- 這份檔在同一天之內從 `0` 變成 `126,428,721`
- **兩個值都是 mid-period 的中間態**，都不是該週的最終值
- 而任何人在任何時刻讀它，**都無法從內容分辨自己拿到的是最終值還是中間值**

這正是 §2 說的「這份資料無法自我描述」。我不必再論證這個風險——它在我寫這份文件的
過程中發生了一次。

## 8. 另一類缺陷（F5，與 F1 無關）：期間結束後寫的報表也低估

`weekly_2026-07-19.json` **不在**上面那張表裡——它的 mtime 是 2026-07-27 07:28，
在期間（07-19 → 07-26）結束之後，所以它通過 `_report_covers_its_period()`，被視為完整。

但它報 **19,844,277**，而本部門獨立 telemetry 重算光 **07-21～07-25 五天**就有
**78,116,380**。也就是說它至少低估 **58,272,103（≥2.9 倍）**。

佐證：它的 `unique_sessions` 是 **63**，而相鄰週分別是 516（07-05）、390（07-12）、
726（07-24）、799（07-26）。單週掉到 63 不合常理。

**這不是 F1 能解釋的**——F1 是「期間沒結束就寫」，而這份是期間結束後才寫的。
根因本部門不推測（屬 platform_eng 判定），只交證據與量級。標記為 **F5**。

## 9. §1 的一句話結論要補一個分支

原結論「不該回填」只針對 `weekly_2026-07-31`，成立不變。補上完整版：

> **判準是「期間結束了沒」＋「機制認不認為它 due」，不是「內容是不是 0」。**
> - 期間未結束 → 0 或中間值都正常，**不回填**（`weekly_2026-07-31`、`weekly_2026-08-02`）
> - 期間已結束、機制標 due → **等它自癒**，不人工回填
> - 期間已結束、機制**不會**重產 → **這才是真缺陷，該回填**
>   （`weekly_2026-05-29` 至 `weekly_2026-06-26` 五份，以及 F5 的 `weekly_2026-07-19`）

第三個分支正是我前三輪從來沒問到的那一題。
