# 報表可信度與缺陷排序判準

三條規則，都是踩過坑歸納出來的。**每條都附「我當初怎麼答錯的」**——因為錯的直覺
比對的規則更容易復發。

---

## 規則 1：改口 ≥2 次 → 去看那份資料能不能自我描述

**觸發**：發現自己（或前一輪的自己）對**同一個欄位／同一個判斷**改口 ≥2 次。

**錯誤反應**：再改一次結論，把措辭寫得更小心。
**正確反應**：停下來問「**為什麼我會反覆答錯同一題**」。答案通常不在我身上，
在那份資料——它缺了能回答這題的欄位，所以每次都得靠外部線索去推斷，推斷就會飄。

**動作**：
1. 列出「回答這題需要哪些事實」
2. 打開 payload，逐項確認它有沒有帶這些欄位
3. 缺哪個，缺的那個就是要修的東西（改資料格式，不是改我的措辭）

**實例（2026-08-05，`weekly_2026-07-31.json`）**：三輪說法是「需回填」→「不需回填」
→ 清單裡又寫成「已知壞、還沒人動」。往定義挖之後發現 payload 沒有 `generated_at`、
沒有 `period_end`、沒有 `period_complete`——「這個 0 是還沒發生還是漏記了」
**光讀檔案答不出來**，完整性存在檔案 mtime 裡，不在報表內容裡。

**這條規則的價值不在修好那一題**：順著它挖出 47/98 份報表寫在期間結束前、
五份 weekly 永久凍結在部分期間值、F5 這個全新缺陷、mtime 不隨 git 走的移機風險。
只改結論的話，這四件一件都不會被發現。

---

## 規則 2：報表可信度看「期間結束了沒 ＋ 機制認不認為它 due」，不看內容是不是 0

讀到任何一份 token／統計報表，先走這棵樹，**不要從 `totals == 0` 起跳**：

1. 期間**未結束**（先讀 `week_range` / `date`）→ 0 或中間值都正常，**不是缺陷**，停。
2. 期間已結束、`build_token_usage_maintenance()` 標它 `due` → **會自癒**，等它跑，
   不人工回填。
3. 期間已結束、機制**不會**重產 → **真缺陷，該回填**。

**第 3 分支是最常被跳過的那一題**：前三輪我從沒問到它，所以每次都在 1 和 3 之間亂猜。

**現場實證**：2026-08-05 17:37:56 dispatch-supervisor 例行跑重產
`weekly_2026-07-31.json`，值從 `0` → `126,428,721`，而該週還沒結束——同一天內兩個值、
**兩個都是 mid-period 中間態**，讀的人無法從內容分辨。這就是為什麼判準不能是內容。

---

## 規則 3：排優先序時，「通過了檢查的錯誤」永遠排在「顯眼的錯誤」前面

一句話：**0 很顯眼會被抓到；部分期間的非 0 值不會有任何人懷疑。**
一個明顯錯的數字會被修，一個看起來合理的錯數字會被引用。

排序：
- 「通過了完整性檢查的錯誤」 > 「沒通過檢查的錯誤」——前者會被當基準用（F5 就是這型：
  mtime 在期間之後、通過檢查、被視為可信，但低估 ≥2.9 倍）
- 「看起來正常的錯值」 > 「顯眼的 0」——後者自帶警報，前者靜默擴散
- 已對外的錯值 > 只在內部的錯值（對外通道盤點見 `memory/notes.md`「對外口徑地圖」）

---

## 三條規則的共同形狀

都是在說同一件事：**不要相信「看起來對不對」，去問「這份資料有沒有能力回答我的問題」。**
沒有能力回答的，任何直覺都是猜的——包括我自己覺得很有把握的那次。
