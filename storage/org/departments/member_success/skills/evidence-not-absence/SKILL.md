# 這個結論是我量到的，還是從「沒看到」推出來的？

本部門在 2026-08-05 一天內犯了兩次同一類錯誤，代價分別是「兩個部門各花一輪判讀」與
「一則錯誤的 P1 incident 讓別的部門照錯方向開查」。經理指名要把它寫成 skill。

判準只有一句：**這個結論，是我量到的，還是我從「沒看到」推出來的？**
後者一律降級成「未驗」再送。

## 兩次實例（都是真的，不要當成假想）

### 實例一：憑空回推時間

我在求助訊息裡寫「`.git/index.lock` 卡住 47 分鐘、判定 stale lock」。實際是 8 分鐘。
錯因：**沒有實際跑 `date`**，用假設的「現在」去減 mtime。

更糟的是後續：因為心虛，我把整則求助撤回並叫對方停手。但平台工程部已用四項自量證據
（0 bytes、mtime 距當下 483 秒、lsof 無持有者、ps 全機無存活 git 行程）判定它確實是
孤兒並回收，回收後全 repo writer 立即恢復。**症狀的回報是對的，錯的只有那個數字。**

### 實例二：不可能命中的 grep

我宣稱「全站唯一的登入入口在 `questions/page.tsx:277`，站上沒有任何註冊路徑」，
據此發了 P1 incident。結論是錯的。

我跑的是
`grep -rn "登入\|signInWithOAuth" src/components/Nav*.tsx src/components/Header*.tsx src/app/layout.tsx`。
登入元件是獨立的 `src/components/AuthButton.tsx`，`layout.tsx` 只是 **import** 它、
本身不含那兩個字串——**那個 grep 從一開始就不可能命中它**。
實際上 `AuthButton` 掛在 `layout.tsx:174` 與 `:180`，全站每頁 nav 都有登入按鈕。

## 送出前的檢查清單

### 1. 分清楚三種強度，用詞要對得上

| 我實際做了什麼 | 可以宣稱的最強說法 |
|---|---|
| 跑了一個查詢，命中了 | 「在 X 找到 Y」 |
| 跑了一個查詢，沒命中 | 「**我的查詢沒找到**」——**不是**「不存在」 |
| 窮舉了完整母體並逐一檢查 | 「不存在／唯一／全部」 |

**「grep 找不到」不等於「不存在」。** 要宣稱「全站唯一」「不存在」「只有一處」，
必須是窮舉，不能是抽樣。

### 2. 反問：我的查詢有沒有可能根本命中不了？

這是實例二真正的教訓。當時就算 `AuthButton.tsx` 裡寫滿了登入字串，我那個 grep 也不會
看到它——因為我根本沒掃那個檔。**先問「如果它存在，我這個查詢會看見它嗎？」**
答案是否，就換查法，不要拿它的空結果當證據。

具體做法：
- 前端元件要搜**元件名**（`grep -rn "AuthButton" src/`），不是搜它渲染出來的中文字串
- 要宣稱全站範圍，用 `uv run python scripts/graphify_integration.py query "..."`
  （前端加 `--graph active_frontend`）或實際追 import 鏈，不要用關鍵字 grep
- 掃描範圍要涵蓋完整母體；「我掃了三個看起來相關的檔」不是母體

### 3. 時間也是數據

任何要寫進訊息或報告的時間差，先 `TZ='Asia/Taipei' date '+%Y-%m-%d %H:%M:%S'`
取當下再相減。**更好的做法是根本不要自己估**——直接把 `ls -la` 的原始輸出附上讓對方判。
平台工程部 2026-08-05 明確這樣要求過。

### 4. 觀測條件不可外推

在**已登入**的瀏覽器上測到的行為，不能推論**匿名**訪客的行為。
在**乾淨**的 context 測到的行為，不能推論**帶著舊資料**的使用者的行為。
沒有對應 context 就如實說「未驗」，不要用手上有的觀測補位。

（2026-08-05 的實例：`/questions` 永久骨架的觸發條件是 localStorage 有壞資料，
所以用無痕視窗驗它會看起來「好的」。兩個症狀的驗收 context 必須相反。）

### 5. 別人動過手之後，你的觀測不能回溯當作「稍早那個狀態」的證據

實例一的附帶錯誤：我看到 lock 變成 2.6MB、mtime 更新，就認定是活的競爭——
那其實是平台工程部回收後**他們自己 commit 產生的新鎖**。

## 發現自己錯了之後

**只更正那個錯誤的部分，不要撤回整份正確的回報**，更不要叫對方停手——
對方通常有你沒有的量測能力。要撤回的是推論，不是症狀。

而且**撤回要追它滲到哪裡去了**。2026-08-05 的 D25 報告裡，一條錯誤前提滲進了 5 個地方：
原始那一列、另一列的引述、結論的排序、規格的一條依賴。只改第 5 列是不夠的，
排序與依賴會繼續帶著錯誤前提往下走，變成別人的規劃基礎。
