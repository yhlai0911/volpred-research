## 1. 四個維度，一個根因

| # | 症狀 | 被當成誰的 bug |
|---|---|---|
| 1 | 相對 pattern 解析成 settings 檔所在目錄的相對（`storage/drafts/**` → `storage/org/runtime/storage/drafts/**`）；七部門全數寫入被拒 | `org_attach` |
| 2 | `rstrip("/")+"/"` 使檔案宣告變成 `storage/org/policy.md/**` | `org_attach` |
| 3 | 點開頭目錄不被萬用字元命中 | `org_attach` |
| 4 | `org_admin.py:202` 在**寫進 registry 之前**就 `rstrip('/')+'/'`，registry 存的是 `storage/org/policy.md/`，於是 `org_attach` 的檔案偵測**永遠看不到檔案** | 端到端 |

**前三次都被當成 `org_attach` 的 bug。第四次證明不是。**
`owned_paths` 這個資料型別從頭到尾**沒有定義過它存的是什麼**——目錄？檔案？路徑前綴？glob？
兩個地方各自用字串拼接去猜（`org_admin` 存的時候、`org_attach` 生成的時候），
**修其中一個不會贏**：`org_admin` 先把檔案變成目錄，`org_attach` 再怎麼偵測都偵測不到。

這正是 CLAUDE.md 3-strike 條款指的「wrong domain model」，不是三個 patch 點。

## 1.1 回讀 registry 發現的第五種形狀（本計劃書新增，尚未被任何維度涵蓋）

```
research: ['.claude/worktrees/*/experiments/', 'experiments/']
```

**`owned_paths` 裡已經有一條帶內嵌萬用字元的宣告在生產環境跑著。**
現行 `rstrip("/") + "/" + "**"` 對它剛好能用，是運氣不是設計。
任何「檔案 vs 目錄」的二分型別**都會漏掉它**——所以型別不能是二分的。

## 2. 契約：`owned_paths` 的每一項都是「路徑模式」，不是路徑

**型別定義（單一來源，寫進 `_core.py` 的 docstring，兩端共讀）**：

> `owned_paths` 的每一項是一個 **repo-relative 路徑模式**，語意由它自己的字面決定：
> - 以 `/` 結尾 → **目錄前綴**，涵蓋其下全部內容
> - 不以 `/` 結尾且不含萬用字元 → **精確路徑**（可能是檔案，也可能是目錄本身）
> - 含 `*` → **glob 模式**，逐字使用，不得加工

**三條不變式**：

- **I1（不可加工）**：`org_admin` 寫進 registry 的字串，必須與使用者宣告的**逐字相同**。
  正規化只允許發生在**渲染時**，不得發生在**儲存時**。
  → 直接廢掉維度 4 的根因（`org_admin.py:202` 的 `rstrip('/')+'/'`）。
- **I2（單一建構器）**：由 registry 項產生權限規則的邏輯**只能有一份**，
  住在 `_core.py`，`org_attach` 呼叫它。**任何地方不得再出現第二處字串拼接。**
- **I3（自我驗證）**：建構器產出規則後，必須能回答「這條規則匹配得到我宣告的目標嗎」，
  匹配不到即 **raise，不得靜默產出**。
  → 這是前四次共同缺席的東西：四次全都靠「有人回報寫不進去」才發現。

**I1 有一個必然後果，要寫進 bulletin**：registry 現存 7 個部門的值全部帶尾斜線
（其中一條含 glob）。啟用 I1 後它們的語意**不變**（帶 `/` 就是目錄前綴），
**所以不需要資料遷移**。這是刻意設計的——需要遷移的契約在這個階段不該採用。

## 3. 驗收（表格驅動測試，platform_eng 既有那支再補列）

**五個維度＝五列，四個來自事故、一個來自生產環境現值。不必自己想案例。**

| 列 | 宣告 | 期望 | 出處 |
|---|---|---|---|
| a | `storage/drafts/` | 絕對前綴 + `**`，且**不**相對於 settings 檔位置 | 維度 1 |
| b | `storage/org/policy.md` | 精確匹配該檔；**不得**變成 `policy.md/**` | 維度 2 |
| c | `.claude/rules/` | 點開頭目錄**必須**被命中 | 維度 3 |
| d | `storage/org/policy.md` 經 `org_admin set-paths` 存入後**再**渲染 | registry 存的仍是 `storage/org/policy.md`（未被加尾斜線），渲染結果同 b | 維度 4（**端到端**） |
| e | `.claude/worktrees/*/experiments/` | glob 逐字保留，不得被加工 | 生產現值（§1.1） |

**d 列是端到端而非單元層**——維度 4 的教訓正是「兩端各自單元測試都會過」。

**額外一項（非測試，是人工回讀）**：維度 3 修好後回測 `.claude/rules/` 是否解封（見 §1.2）。

## 4. 為什麼這次要有計劃書，而 D55 (b) 那次不要

我在 14:03Z 反對過一次，經理採納。**兩次的差別不在事故次數，在根因層級**：

- 那時：三個維度全部指向 `org_attach` 的檢查缺席，而 D53 修的就是那道缺席的檢查
  → **修法已經在根因層級，再開計劃書是疊層。**
- 現在：維度 4 證明根因**不在任何單一函式**，而在一個沒有定義的資料型別，
  它跨越兩個檔案與一次序列化
  → **沒有任何一支函式的修法能涵蓋它**，契約必須寫在兩端之外。

**計劃書的觸發條件不是「第 N 次」，是「修法的作用域小於根因的作用域」。**
前一次不是，這一次是。
